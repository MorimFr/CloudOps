## Arquitetura planejada

```text
CIS controls (ID, fonte, versão e profiles imutáveis)
  → collector requirements
  → shared collectors
  → normalized facts + cobertura + capability context
  → deterministic evaluators versionados / revisão humana
  → evidence sanitizada
  → finding (resultado CIS separado de risco CloudOps)
  → report / AI advisory futuro
```

Cada CIS ID permanece independente. Deduplicar consultas e fatos, nunca controles. Related controls organizam correlação e roadmap, sem modificar resultados. Não há score subjetivo de priorização.

## Resultados, contexto e evidência

PASS exige todos os critérios comprovados; FAIL exige violação comprovada com coleta suficiente. 403, licença não comprovada, campo ausente, PARTIAL e ambiguidade relevante → UNKNOWN. Falha técnica irrecuperável → ERROR sanitizado. Inacessibilidade não é não conformidade. Caminho humano → MANUAL; dados técnicos auxiliares não substituem atestação.

Fora do profile é não selecionado, não N/A. NOT_APPLICABLE requer aplicabilidade expressamente falsa conforme a fonte, comprovada por contexto (por exemplo cloud-only em controle explicitamente híbrido). Não inferir topologia por endpoint ausente. Sensibilidades a IdP externo, federação, sincronismo e break-glass estão registradas por controle.

Wave 1 usa contagens/booleans/enums allowlisted. IDs de joins vivem somente em RAM. Referência de objeto apenas quando necessária à revisão humana, sem UPN/displayName e nunca no AI input. Exceção aprovada separada de frameworkStatus: FAIL + accepted risk permanece FAIL. Nenhuma persistência foi criada.

## Gaps com a foundation existente

- FactsSchema aceita até 64 chaves allowlisted com integer/boolean/null, não arrays/objetos/raw Graph. Wave 1 requer apenas novos nomes escalares aprovados. Enums terão codebook fechado e unknown/presença explícitos; nenhum default silencioso.
- CA, PIM e reviews exigem projeções tipadas, limitadas e versionadas antes de implementação. Não esconder predicates CIS nos collectors para contornar o contrato: collectors observam fatos, evaluators comparam requisitos.
- HYBRID atualmente retorna MANUAL no SDK. Coleta auxiliar e atestações são um design futuro explícito, não uma funcionalidade já implementada.
- Control IDs atuais não aceitam pontos: planejar ID interno seguro, como cis-m365-5-1-2-2, mais cisId literal separado; não relaxar o contrato global.
- Loader atual é basename-only. A árvore versionada futura exige extensão explícita, não descoberta recursiva de JSON arbitrário.
- Metadata CIS, novos scopes e novas áreas do report precisam contratos e testes futuros. Nenhum enum/manifest runtime foi ampliado nesta fase.
- O adapter futuro precisa distinguir reason codes de 403/cobertura (UNKNOWN) de falha técnica (ERROR), sem converter FAILED genericamente em lista vazia.

## Report e AI planejados

Finding futuro: CIS ID, title, profiles, CIS Assessment Status, CloudOps Result, CloudOps Risk, Evidence, Observed, Expected, Recommendation, Portal Path, Implementation Impact, Validation e Benchmark source/version. Caminhos de portal/remediação serão sínteses revisadas com referência de página, não cópia integral do PDF.

Framework: PASS / FAIL / MANUAL / NOT_APPLICABLE / UNKNOWN / ERROR. Risco separado: LOW / MEDIUM / HIGH / CRITICAL. Nenhum score ou LLM foi implementado. AI advisory futuro recebe somente control ID, status, risk e fatos sanitizados allowlisted, nunca raw Graph, tenant objects, tokens ou PII; jamais altera o resultado CIS.
